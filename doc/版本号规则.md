# 版本号规则

蔷薇前端有**两个各自演进的版本号**：脚本一个，配套数据库模板一个。
两者靠**代号**配对，不靠数字对齐。

## 格式

```
<主版本>[热修字母]-<代号>

1.0-RosaCaninae            模板 1.0
1.0a-hotfix-RosaCaninae    脚本 1.0 的第一次热修
```

三段的含义：

| 段 | 何时变 |
| --- | --- |
| **主版本** | 功能增删、界面改版、行为变化 |
| **热修字母** | 修 bug、改文案、调时序、提升健壮性与兼容性 —— 追加 `a` `b` `c`… |
| **代号** | **仅当数据库模板的结构变更时** |

主版本与热修字母的界线是**用户看得见的功能有没有变**：

- 多了或少了一样能用的东西、界面改了样子、原有操作的结果变了 → 主版本
- 原本就该那样、只是之前没做好 → 热修字母

按这条线，**兼容性改进属于热修**。让脚本适应更多外部数据库模板、
把失配时的空白改成说明、认不出结构时把模块干净隐藏 —— 这些都不是新功能，
而是原本就该有的表现。用户不会觉得「多了个功能」，只会觉得「这下正常了」。

## 什么时候动哪一个

**热修**在主版本号后加一个字母，`-hotfix` 后缀写不写都行，写上更醒目：

```
1.0  →  1.0a-hotfix  →  1.0b-hotfix
```

热修不动数据结构，因此**代号不变、模板不必重新导入**。这是最常见的情形，
用户看到脚本版本变了而模板没变时不该产生困惑 —— 教程里那条「认代号，
不认小版本」的说明就是为此存在的。

**代号只在模板结构变更时更换**：加表、删表、改列名、改 CHECK 约束这类。
换代号意味着旧模板与新脚本不再配套，用户必须重新导入模板。

这是一次破坏性变更，而**承载这个信号的是代号本身，不是数字**。
所以数字怎么走都行 —— `1.0` 换代号时进到 `1.1` 完全可以，不必跳 `2.0`；
反过来只把 `1.0` 改成 `1.1` 而代号不变，则绝不能表示破坏性变更。
判断配不配套**只看代号**：

```
脚本 1.0b-hotfix-RosaCaninae  ✓  模板 1.0-RosaCaninae      代号相同，配套
脚本 1.2-RosaCaninae          ✓  模板 1.1-RosaCaninae      代号相同，配套
脚本 1.1-RosaRugosa           ✗  模板 1.0-RosaCaninae      代号不同，须换模板
```

## 代号取自蔷薇属

代号从 **蔷薇属（*Rosa*）的组或物种**里挑，写成 `Rosa` + 名称的驼峰形式。

现用的 `RosaCaninae` 取自**犬蔷薇组**（*Rosa* sect. *Caninae*）。

后续可选的组：

| 学名 | 中文 |
| --- | --- |
| sect. *Cinnamomeae* | 桂味组 |
| sect. *Synstylae* | 合柱组 |
| sect. *Gallicanae* | 法国蔷薇组 |
| sect. *Pimpinellifoliae* | 密刺组 |
| sect. *Banksianae* | 木香组 |
| sect. *Laevigatae* | 金樱子组 |
| sect. *Bracteatae* | 硕苞组 |
| sect. *Carolinae* | 卡罗莱纳组 |

或直接取物种：*R. chinensis*（月季）、*R. rugosa*（玫瑰）、*R. banksiae*（木香）、
*R. laevigata*（金樱子）、*R. multiflora*（野蔷薇）、*R. gallica*（法国蔷薇）、
*R. moschata*（麝香蔷薇）、*R. gigantea*（巨花蔷薇）。

选过的代号不再复用 —— 代号的作用是标识一代数据结构，复用会让历史存档
无法判断该配哪份模板。

## 版本号写在哪

**脚本版本号只有一处来源**：

```
src/BaraFrontend/domain/plugin-license.ts
export const PLUGIN_VERSION = '1.0a-hotfix-RosaCaninae';
```

`pack-script.mjs` 用正则从这个文件里读它，然后决定三样东西：

- 产物文件名 `Script-BaraFrontend-${VERSION}.json`
- 脚本列表里显示的名字 `蔷薇前端 ${VERSION}`
- `info` 字段首行

**不要在别处另写一份**。两处各写一份，日后必然改了一处忘了另一处，
而「界面上显示的版本与产物里的版本对不上」是最难察觉的一类错：
两边单独看都没问题。

发版时改这一行，跑 `pnpm build:tavern` 即可。

**模板版本号**写在文件名里，没有程序读取它 —— 它纯粹给人看。

## 产物文件名

脚本与模板成对，用同一套前缀：

```
Script-BaraFrontend-<主版本>[热修字母]-<代号>.json    脚本
Preset-BaraFrontend-<主版本>-<代号>.json              数据库模板

Script-BaraFrontend-1.0b-hotfix-RosaCaninae.json
Preset-BaraFrontend-1.0-RosaCaninae.json
```

用 ASCII 前缀而非中文名：下载目录里两者相邻排列，一眼能看出是一套，
也不必担心不同系统下中文文件名的编码问题。

> 历史遗留：`数据库模板-BaraFrontend-1.0-RosaCaninae.json` 与
> `蔷薇前端-<版本>.json` 是旧写法。现在改名会让已发布的 release 附件与
> 教程截图对不上，因此**留到下次换代号时**随模板一并规整 ——
> 那时用户本来就要重新下载两个文件。

## 发版时要一起改的地方

改 `PLUGIN_VERSION` 之后，这几处引用了版本号的文档需要跟着更新：

- `README.md` 顶部的版本行与「快速开始」里的文件名
- `发布/蔷薇前端-使用教程.md` 顶部的版本行
- 使用教程的「近期更新日志」栏目 —— 按 `26w32` 这样的 ISO 年周编号分组
- `发布/` 目录里的旧产物要删掉，避免留下两个版本的 json

## 已规划

| 版本 | 内容 | 用户要做什么 |
| --- | --- | --- |
| 脚本 `1.0b-hotfix-RosaCaninae` | 跨模板兼容 —— 适应外部数据库模板、失配时给出说明 | 无，模板不变 |
| `1.1-<新代号>` | 重要角色表加入恋爱相关内容（模板结构变更） | **必须重新导入模板** |

跨模板兼容走热修字母而非主版本，理由见上文「主版本与热修字母的界线」：
它让脚本在别人的模板下表现正常，不新增用户可见的功能。

这两件事**不要合并发版** —— 前者用户无感，后者强制重导模板；
合在一起会让兼容性改进的收益被「又要重新导入」的成本盖掉。

换代号时一并把两个产物的文件名规整为上文「产物文件名」定义的样式。
