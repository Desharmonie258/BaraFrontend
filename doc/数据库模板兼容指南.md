# 为蔷薇前端开发兼容的数据库模板

写给**数据库模板的作者**：你想让自己那份模板在蔷薇前端上把功能点亮，
需要满足哪些约定。

前提先说清楚：**蔷薇前端只是显示层**，表格数据的存储与填写由 SP·数据库负责。
本文只讲「前端怎么认你的表」，不涉及 note 怎么写、AI 怎么填。

---

## 零、最低要求：什么都不做

不做任何适配，你的模板也能用 —— 表格坞会列出全部表，卡片视图与列表视图
把每张表原样显示出来。**这是保底，不需要任何配合。**

需要配合的是那些「按语义组织数据」的功能：仪表盘、角色卡、检定、地图、
交互总览。它们要知道「哪张表是角色表」「哪一列是属性」，才有东西可显示。

还有一条硬要求与模板无关但常被卡住：**数据库存储模式必须是 SQLite**。
留在原生 JSON 模式下面板能开，但角色卡里大部分分区会是空的。

### 认不出不会报错

前端的一贯做法是：**认不出的功能整块隐藏**，而不是显示一个点不动的空面板。
所以你看到某块没有，不代表坏了，是那张表没认出来。

去 **设置 →「模板适配情况」** 看每项能力认到了哪些表、经由哪条通道。
指纹命中的会标注「按列结构推测」—— 那是推测，万一认错了，这行标注是唯一线索。

浏览器控制台执行 `BaraFrontend.diagnose()` 能拿到更全的信息：
每张表的 key、展示名、物理表名、行数、结构判定与完整列名。

## 一、前端怎么认出一张表

三条通道**并列**，任一命中即可，不存在谁优先：

| 通道 | 匹配什么 | 什么时候有用 |
| --- | --- | --- |
| **sheet key** | 表的内部标识 | 从官方模板衍生、保留了原 key 的模板 |
| **展示名** | 表名 | key 被重制、但表名规规矩矩的模板 |
| **列名指纹** | 若干列**同时**存在 | key 与表名都对不上，只能靠列结构辨认 |

key 失效于重制，表名失效于改名，两者覆盖的场景互不相同 —— 所以并列而非分优先级。

### 指纹要求多列同时命中

这是刻意的。指纹最危险的失败模式是**误命中**，而误命中比不命中难查得多：
不命中会显示明确提示，误命中会显示**一份看起来正常的错误数据**。

真实教训：角色表的指纹曾把「主角信息表」误认成角色表 —— 两者列结构几乎一样，
十份模板里七份中招，后果是主角在「重要角色」列表里重复出现一遍。单元测试
完全看不出来，是拿十份真实模板横向跑才发现的。

所以：**宁可判不出，也不要判错。**

### 认不出时的兜底：仪表盘预设

如果你的表名实在对不上内置候选，又不想改表名，可以让用户导入一份
**仪表盘预设**（设置 →「模板适配情况」最下方），给识别层补一组表名关键词。

```jsonc
{
  "format": "acu_dashboard_preset_v1",
  "name": "我的模板适配",
  "description": "把关键词换成你那份模板里的叫法",
  "modules": {
    "npc":    { "tableKeywords": ["登场人物", "出场角色"] },
    "bag":    { "tableKeywords": ["随身携带"] },
    "equip":  { "tableKeywords": ["穿戴"] },
    "global": { "tableKeywords": ["世界状态"] }
  }
}
```

模块名与规格的对应：`npc`/`player` → 角色表，`bag` → 物品表，
`equip` → 装备表，`global` → 全局数据表，`relationshipGraph` → 关系表。

三条要点：

- **只在内置识别认不出时才生效。** 已经能认出的表不受预设影响 ——
  内置那套有十份真实模板的回归测试兜着，用户手填的关键词不该盖过它。
- 表名**包含**任一关键词即命中，不区分大小写。
- 格式与骰子系统的仪表盘预设通用，两边可以互相导入。

> 预设只改「哪张表是什么」，**不改布局与渲染**。一旦允许预设改布局，
> 它就变成了没人维护得动的小型模板语言。

## 二、各功能要哪张表

下表的「表名候选」是内置的展示名清单；**用其中任意一个名字最省事**。

| 功能 | 表名候选 | 指纹（需同时具备） |
| --- | --- | --- |
| 角色（仪表盘、角色卡） | 角色表 / 追踪角色表 / 重要角色表 / 重要人物表 / 恋爱对象表 | `姓名` `基础属性` `特有属性` |
| 主角（旧结构） | 主角信息 / 主角信息表 | 无 |
| 检定建议 | 检定建议表 | `展示文本` `骰子命令` |
| 物品 | 物品表 / 背包物品表 / 重要物品表 | 无 |
| 装备 | 装备表 | 无 |
| 角色资源 | 角色资源表 | `资源ID` `当前值` `上限` |
| 当前局面 | 全局数据表 / 全局数据 / 世界状态表 / 全局状态表 | `当前时间` |
| 关系图 | 关系表 / 人物关系表 / 关系网络表 | `角色A` `角色B` |

**角色表可以有多张。** 有些模板把角色拆成「恋爱对象表」与「重要角色表」两张并列的表，
前端会全部读取 —— 只读一张会让另一张的角色整个消失，且消失的是哪张取决于
枚举顺序，是一种很难察觉的数据缺失。

**主角是角色表里的一行，不必单独建表。** 自 1.1 起自家模板已把主角并入角色表，
靠 `姓名` 匹配 persona 名来定位；找不到时退而找第一个 `角色定位` 为 `永固` 的行。
旧的分表结构仍然认，不必为此改模板。

## 三、列的约定

表认出来之后，功能能不能点亮取决于列。列一律按**展示名**匹配。

### 3.1 角色表

| 列 | 用途 | 缺了会怎样 |
| --- | --- | --- |
| `姓名` | 定位角色、匹配各分区 | 角色认不出来 |
| `别称` | 分区匹配的备用称谓 | 别名写法的行匹配不上 |
| `身份` | 卡片副标题 | 不显示副标题 |
| `基础属性` | 属性网格、检定 | 无属性可点、无法检定 |
| `特有属性` | 角色卡的特有属性区 | 该区不显示 |
| `所在地点` | 卡片脚注 | 不显示 |
| `在场状态` | 「在场 / 全部」筛选 | 一律按离场处理 |
| `角色定位` | 值为 `永固` 时可作主角兜底 | 主角定位少一层保险 |

`在场状态` 的值要恰好是 `在场`；其余值一律当作离场。

### 3.2 属性打包串

**基础属性与特有属性各占一列**，一列里放该角色的全部属性：

```
力量:19; 敏捷:64; 体质:50
```

分号分隔，分号后可有可无空格，末尾分号可有可无。

特有属性可再带第三段「关联的基础属性」，可省略：

```
野猪狩猎:7:敏捷
```

三条纪律：

- **数值非法时不会被丢弃**，前端保留原文并标记 —— 不吞用户数据。
- **序列化保持原有顺序**，新属性追加到末尾。顺序一变，AI 每轮都会
  误判成「有改动」。
- 手改会按当前规则族的区间钳制，改数值不会把第三段抹掉。

### 3.3 角色资源表

| 列 | 说明 |
| --- | --- |
| `持有人` | 关联角色 |
| `资源ID` | 稳定标识，用于固定排序 |
| `显示名` | 界面显示的名字 |
| `当前值` `上限` | 数值。上限缺失时不画进度条 |
| `恢复策略` | 标签显示（长休 / 场景…） |
| `置顶` | `是`/`true`/`1`/`yes` 之一时上角色卡头部 |

四条默认资源的**展示顺序固定**（生命值 → 耐力值 → 饱腹度 → 性欲值），
按 `资源ID`（`hp`/`stamina`/`satiety`/`libido`）或显示名回配。
AI 插行的先后不定，按行号展示会让同一个角色在不同存档里资源条排列不一样。

其余资源按行号排在默认资源之后。

### 3.4 角色卡各分区

角色卡把十余张表按角色聚合。**每张表靠哪一列关联角色并不统一**，
这是数据结构的历史差异，前端把它们集中处理：

| 分区 | 表名 | 关联列 |
| --- | --- | --- |
| 技能 | 技能表 | `持有人` |
| 装备 | 装备表 | `持有人` |
| 物品 | 物品表 | `持有人` |
| 特性 | 特性表 | `持有人` |
| 状态 | 状态表 | `持有人` |
| 生理 | 重要角色生理 | `姓名`（每角色至多一行） |
| 心理 | 重要角色心理 | `姓名`（每角色至多一行） |
| 大事记 | 追踪大事记 | `记录者` |
| 亲密经历 | 性爱生涯实录 | `主角外对象` |
| 关系 | 关系表 | `角色A` 或 `角色B`，任一命中 |

关联用**包含**匹配而非全等（`记录者` 可能写成「笹兵卫（多默）」这类带补充的形式），
但只对长度 ≥2 的称谓做包含匹配，避免单字名误命中。

`性爱生涯实录` 的 `主角外对象` 记的是**对方**，每一行都隐含主角参与，
因此主角看到全部行、其他角色只看到自己作为对象的那些 ——
这是数据结构决定的不对称，不是设计选择。

### 3.5 人物小传的分组

生理与心理两张表在传记页**合并成连续的阅读内容**，不显示两表的分界。
分组由列名决定，列名不在下表里的**不会显示**：

| 分组 | 列 |
| --- | --- |
| 近期变化 | 近期情绪状态、对主角的互动逻辑、被强化的性格侧面、被弱化的性格侧面、行为模式变化、生理状态 |
| 外貌形象 | 相貌、常用发型、身高/体重、身材/特异性征、体格/胸围、胸膛外观、腰腹外观、臀部外观、腿部外观、体毛、清洁度 |
| 性格 | 性格主色调、主色调衍生一、主色调衍生二、主色调衍生三、主色调用语把捉、性格底色、底色衍生一、底色衍生二、底色衍生三、底色用语把捉、性格点缀、点缀衍生一、点缀衍生二、点缀衍生三、点缀用语把捉 |
| 履历与声部 | 履历、他者声部、作者声部 |
| 身体特征 | 口腔、肩颈腋窝、肌肤触感、身体气味、阴茎与阴囊、后庭剖面、肛门、足码/脚型、足部外观、泌乳与特殊体液、敏感部位、龟头与包皮、前列腺 |
| 性向与经验 | 喜好日常衣物、喜好NSFW衣物、喜好体位1、喜好原因1、喜好体位2、喜好原因2、喜好玩法、喜好原因3、拒绝性爱方式、床上淫语风格、性偏好部位、事后状态习惯、主角初次记录、性经验、性技巧、最近性行为、主角性爱次数 |

「近期变化」置顶并有视觉区分 —— 它是唯一随剧情变动的部分，
与静态设定混排会让人看不出哪些是「当下」、哪些是「设定」。
后两组默认折叠。

**列名必须与上表完全一致**，同义词不认 —— 这份分组是写死的清单，
不是关键词匹配。多出来的列不会丢失（它们仍在表格坞里），只是不进小传。

分区内**空值列整条隐藏**，不显示「暂无」：阅读性内容里一屏「暂无」
会显得残缺，实际只是该角色尚未展开到那个细节。

### 3.6 检定建议表

四列，**按名字认，认不出时退回列位置**：

| 列 | 备用关键词 | 位置兜底 |
| --- | --- | --- |
| `建议类型` | 含「类型」 | 第 1 列 |
| `发起者` | 含「发起」 | 第 2 列 |
| `展示文本` | 含「展示」 | 第 3 列 |
| `骰子命令` | 含「命令」 | 第 4 列 |

位置兜底的存在意味着：**即使列名完全不同，只要顺序对，建议栏仍能用。**

`建议类型` 含「快进」归为推进类，含「角色」归为角色行动，其余算主角行动。
展示文本为空的行整条丢弃 —— 那是没填的槽位，渲染成空按钮只会让人以为坏了。

### 3.7 全局数据表

一行即可（多出来的行不会显示 —— 用户会以为有两个「当前时间」）。

| 字段 | 列名候选 |
| --- | --- |
| 当前时间 | `当前时间` |
| 当前地点 | `当前详细地点` / `当前地点` / `所在地点` |
| 次要地区 | `当前次要地区` |
| 主要地区 | `当前主要地区` |
| 经过的时间 | `经过的时间` |

主要/次要地区还决定**地图打开时停在哪一层**（见 4.2）。

### 3.8 关系表

| 字段 | 列名候选 |
| --- | --- |
| 一方 | `角色A` / `角色 A` / `甲方` / `发起者` |
| 另一方 | `角色B` / `角色 B` / `乙方` / `对象` |
| 描述 | `关系描述` / `关系` / `描述` |

关系图按**无向**处理并去重：模板不必要求双向登记，写一条与写两条方向相反的
得到同一张图。同一对人重复出现时保留先出现的描述，否则出图会随行序抖动。

关系图**只画表里出现过的名字**，不去角色表核对是否建档 —— AI 会写出
「路人甲」这类没有建档的角色，剔掉会让关系图缺一大块。

### 3.9 枚举列

DDL 里写 `CHECK(col IN (...))` 的列会被解析成枚举，界面渲染成一排可点选项。

但**默认只有一处放行给玩家点**：NPC 表（或「普通角色表」）的 `归档状态`。
其余枚举列只显示当前值。

原因：绝大多数枚举列是 AI 依剧情写的（天气、状态、与今天的关系），
玩家点一下就把叙事改了，而且下一轮 AI 还会覆盖回去 —— 既无效又容易误触。
`归档状态` 是玩家的决定（把谁纳入跟踪），本来就该由玩家来点。

> 用户开启表格的**编辑模式**后，整张表每一格都能改，届时全部枚举列都放开。
> 那是显式操作，与上面这条不冲突。

## 四、视图

视图的开放条件一律**按列探测，不按表名** —— 外部模板的地图表没有坐标列，
认不出即退回卡片视图，而不是给一个点开是空白的地图切换。

### 4.1 日历视图

有**含「日期」的列**即开放。

`小日历表`/`日历表`、`小日记表`/`日记表` 这两类**只开放日历** ——
它们按日排布，用卡片看等于把日历拆散重排一遍，既丢时间轴又更难读。

### 4.2 地图视图

需要 `X坐标` 与 `Y坐标` 两列（先精确匹配，再退到包含匹配）。**缺一列就不开放。**

- 坐标为 `0.00`–`1.00` 的归一化值，`0` 为最西/最南。
- 坐标是**软的**：前端不把它当真值，而是当力模拟的初始位置与弱吸引目标。
  填得准则精确还原，填不准则退化成「方位正确的示意图」，
  而不是糊成一坨重叠的点。

含「接壤」的列会被解析成连线：

```
西大陆:隔海相望; 北境:北邻,山脉阻隔; 御苑:北邻
```

`目标:词,词` 分号分隔。词可以是方位（北邻、东南邻）也可以是连接方式
（街道相连、山脉阻隔），可以都有、都没有。方位字**只在冒号后判断** ——
目标名本身可能含方位字（「西大陆」）。

- **方位比坐标硬**：两者矛盾时以方位词为准，坐标会被修正。
- **无向去重**：只要一侧填了就能画出这条边，漏填对侧不致命。
- 连接方式影响线型：含「山脉/阻隔/关隘」画粗线，含「河道/海/水」画虚线，
  其余实线。
- **两端都在当前层级里才画** —— 跨层级或指向尚未录入地点的关系会被丢掉，
  否则会画出悬空的线。

`世界地图点`/`世界地图点表`、`本地地图表`/`地图元素表` 这几个名字会让
地图成为**默认落点**（仍可切回卡片）。

#### 层级

同时具备 `主要地区`、`次要地区`、`地点类型` 三列（精确匹配）时，
世界地图支持三层下钻。行的层级按填法区分：

| 行 | 地点类型 | 主要地区 | 次要地区 | 名称列 |
| --- | --- | --- | --- | --- |
| 主要地区概览 | `概览` | 自身名 | 自身名 | 自身名 |
| 次要地区概览 | `概览` | 所属主要地区 | 自身名 | 自身名 |
| 详细地点 | 具体类型 | 所属主要地区 | 所属次要地区 | 地点名 |

名称列取**第一个非 `row_id` 列**。

坐标的语义**逐层不同**，都是「在上一级容器内的相对位置」，不是全世界的绝对位置：
详细地点相对所属次要地区、次要地区相对所属主要地区、主要地区相对世界。
所以一张图只画一层 —— 混在一起等于把三套坐标系叠在一起。

地图打开时会停在**玩家脚下那一层**（由全局数据表的当前主要/次要地区决定）；
那一层一个点都没有时逐级往上降，直到有点为止。

## 五、交互总览

交互总览把每张表的每一行摊成一个可点对象。它认表的方式与前面几节**不同** ——
不走 key 与指纹，只按**表名关键词**。

### 5.1 分区归属

表名含这些词就归入对应分区（命中多条取靠前的）：

| 分区 | 关键词 |
| --- | --- |
| 角色 | 主角、角色、人物、NPC、女主、关键人物、重要人物、伙伴、队友、恋爱对象 |
| 地图 | 地点、地图、Location、Map、世界、场所、地区、位置、地标 |
| 物品 | 物品、背包、道具、材料、消耗品 |
| 装备 | 装备、武器、防具、护甲、饰品、装扮 |
| 任务 | 任务、备忘、事项、委托、目标 |
| 技能 | 技能、能力、法术、神通、特性 |
| 势力 | 势力、组织、阵营、派系 |

都不中的落到「通用」栏 —— 认不出分区的表仍然可以有动作。

### 5.2 别让附表被当成对象表

表名含这些词的**整张跳过**，不参与交互总览：

> 资源、属性、生理、心理、临场、记忆、关系、日记、日志、记录、实录、大事记、纪要、小传

原因是一个实测出来的错：「角色资源表」表名含「角色」，被归进角色分区，
而它的第一个非 `row_id` 列恰好是 `持有人` —— 于是**一个角色有几条资源就
出现几次**，实测一个角色刷了 6 遍。「重要角色生理」「重要角色心理」同理。

所以：**给「某个对象的附属数据」表命名时带上上面某个词**，
比如叫「角色资源表」而不是「角色资源」。这既符合直觉，也让前端排得掉。

### 5.3 名称列

每行的名字按这个顺序找：

1. 精确匹配：`姓名` `名称` `名字` `标题` `显示名` `详细地点` `地点名` `地名` `name` `title`
2. 包含匹配：同上
3. 退回第一个非 `row_id` 列

第 3 步有一道把关：第一列若含下列词，**整张表跳过**。它们是**外键**
（指向别的表里的对象），不是这一行自己的名字：

> 持有人、所属、所在、归属、拥有者、主人、角色、对象、类型、种类、状态、等级、数值、描述、备注、说明、序号、编号、id

同一分区内同名对象会被合并成一个，动作取并集。

### 5.4 动作规则

动作也按表名关键词匹配，规则可由用户替换：

```jsonc
{
  "format": "acu_action_preset_v1",
  "name": "我的交互规则",
  "rules": [
    {
      "table_keywords": ["地点", "地图"],
      "actions": [
        { "label": "前往", "template": "<user>前往{Name}。" },
        { "label": "探索", "template": "<user>探索{Name}。" }
      ]
    }
  ]
}
```

- `{Name}` 是对象名，`<user>` 是主角（发送时展开成 persona 名）。
- 多条规则命中时动作**全部合并**，按 label 去重。
- 格式与骰子系统的交互规则预设通用，蛇形键名 `table_keywords` 原样保留。
- **没有任何规则命中的表整张跳过** —— 交互总览回答「我现在能做什么」，
  不是又一个表清单。

## 六、给模板作者的检查清单

按性价比排序，从上往下做：

- [ ] **表名用内置候选之一**（第二节那张表）。这一步能点亮绝大多数功能，
      且不需要任何额外配置
- [ ] 角色表具备 `姓名` `基础属性` `特有属性` —— 即使表名对不上，
      指纹也能救回来
- [ ] 属性写成 `名:值; 名:值` 的打包串，特有属性可带第三段关联属性
- [ ] 各附属表用 `持有人` 关联角色（大事记用 `记录者`，
      亲密经历用 `主角外对象`）
- [ ] 附属数据的表名带上「资源 / 记录 / 生理 / 心理」这类词，
      免得被交互总览当成对象表
- [ ] 地图表加 `X坐标` `Y坐标` 两列（0–1 归一化），
      要三层下钻再加 `主要地区` `次要地区` `地点类型`
- [ ] 检定建议表的四列**按顺序**排：类型、发起者、展示文本、骰子命令 ——
      名字对不上也能靠位置认出来
- [ ] 全局数据表留一列 `当前时间`
- [ ] 导入后去 **设置 →「模板适配情况」** 逐项核对，
      标着「按列结构推测」的要重点确认没认错

改完记得在真机上翻一遍：**误命中不会报错**，它显示的是一份看起来正常的
错误数据，只能靠眼睛发现。
